# Summarize a GitHub PR

1. Identify the PR from the user's number or URL. If outside its repository, pass `--repo OWNER/REPO` or use the URL. If the user omits the PR, resolve the pull request for the current branch with `gh pr view`; ask for a number or URL only when resolution fails or is ambiguous.
2. Choose the interaction mode before drafting:
   - For a clearly read-only request such as explain, summarize, or draft only, produce the draft without asking about approval and never update GitHub.
   - Treat a standalone affirmative `approve` argument as explicit authorization to update the resolved PR's title and body after drafting, without another confirmation.
   - When the user explicitly invokes the skill without a read-only intent, or asks to update without choosing a review mode, ask whether they want to review the draft before it is applied or have it applied automatically. Ask before drafting. In review mode, show the draft and wait for approval; in automatic mode, apply it without another confirmation.
   - If `approve` conflicts with a read-only instruction, ask the user to clarify and do not update GitHub.
3. Run `gh pr view <PR> --json number,title,body,url,baseRefName,headRefName,additions,deletions,changedFiles,commits,files` and `gh pr diff <PR>`.
4. Base the summary on the diff, using commit messages only as supporting context. Do not infer behavior that the changes do not establish.
5. Draft a single-line PR title that summarizes the overall major effort. Prefer the outcome over a list of files or minor changes.
6. Inspect the repository's instructions, manifests, and CI configuration when available so verification suggestions use the project's real commands and practices.
7. Preserve substantive existing body content. If the body contains headings or a template, fill only empty or placeholder sections without replacing substantive text. If it is substantive but unstructured, do not replace it. Use the fallback below only when the body is empty or placeholder-only.

````markdown
## Summary

<concise, outcome-focused overview>

## Changes

- <cohesive behavior or implementation change>
- <feature added>
- <other material change>

## Files

```text
.
├── src/
│   └── package/
│       └── module.py [modified] - Adds delivery-state handling.
└── pyproject.toml [modified] - Includes the new module in the package configuration.
```

## Tests

```text
.
└── tests/
    └── test_module.py [new] - Covers delivery-state transitions.
```

## Verification

- [ ] `<project-specific automated test command>`
- [ ] `<relevant manual verification method>`

*Generated by OpenAI Codex (<exact-model-id>) on YYYY-MM-DD at HH:MM UTC±HH:MM.*
````

Follow this output contract:

- Use the level-two headings exactly as shown and in the same order.
- Write `Summary` as a short paragraph describing the PR's overall outcome.
- Write `Changes` as a flat bulleted list of material changes and features established by the diff. Group related edits, avoid path-by-path narration, and omit unsupported claims.
- Render `Files` and `Tests` as hierarchical trees in fenced `text` blocks. Start each tree with `.`; use repository-relative paths, the Unicode connectors `├──`, `└──`, and `│`, four-column continuation indentation, and a `/` suffix on directory names. Include changed files and only the ancestor directories needed to locate them. Sort sibling directories first and sibling files second, lexicographically within each group; ignore annotations when sorting.
- Annotate every file leaf, including fixtures and binary assets, as `<filename> [<type>] - <summary>`. Leave directory nodes unannotated. Use exactly the lowercase types `new`, `modified`, `deleted`, and `renamed`.
- Derive the type from the unified diff: `rename from` and `rename to` headers mean `renamed`; `new file mode` or an old path of `/dev/null` means `new`; `deleted file mode` or a new path of `/dev/null` means `deleted`; all other changed files are `modified`. Treat mode-only and symlink-target changes at an unchanged path as `modified`.
- Write each file summary as one concise, active-voice sentence on the same Markdown source line as its leaf. Ground it in that file's diff, do not repeat the path or type, and do not insert a line break. For binary, omitted, or otherwise unavailable content, describe only observable facts and use a conservative file or asset description instead of guessing.
- Render a rename once at its destination path as `[renamed] - Moves from <old path>.` Include any material content change in the same sentence. Classify it as a file or test from the destination path, including renames that cross those categories. Treat a copied destination as `new`; include its source only when the source changed independently.
- Classify tests from the repository's established test directories, naming conventions, and configuration. Exclude test paths from `Files` and show them only in `Tests`. When a section has no paths, put `None` as the sole line in its fenced block; do not include `.`, connectors, or indentation in that block.
- Write `Verification` as an unchecked task list using `- [ ]` for every item. Suggest relevant automated commands and manual checks from project instructions, manifests, CI configuration, and affected behavior. Do not mark an item complete or claim that a suggested check was executed.
- Italicize the entire generation footer. Resolve the exact active model identifier from runtime or system metadata; never infer, shorten, or substitute a model family. Use `model identifier unavailable` rather than guessing when the exact identifier is unavailable. For a `gpt-5.6-sol` run, use `gpt-5.6-sol` exactly.
- Use the local system date and 24-hour time with its numeric UTC offset.

Treat the task as read-only unless the user authorizes an update through `approve`, chooses automatic application, or approves a reviewed draft. Authorization covers only the resolved PR's proposed title and body. Apply an authorized update with `gh pr edit <PR> --title "<title>" --body-file <file>`. After success, report the PR URL, applied title, and that the body was updated. If the edit fails, report the failure without claiming success or silently changing the target.
